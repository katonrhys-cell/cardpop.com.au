# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

CardPop is an Australian trading card marketplace. It is a full-stack application with a React SPA frontend and an Express backend, backed by Supabase (PostgreSQL + Auth). The app is deployed on Vercel. The domain `cardpop.com.au` was purchased through Crazy Domains (registrar), but its nameservers now point to Cloudflare (`coco.ns.cloudflare.com` / `clayton.ns.cloudflare.com`) — so **Cloudflare is authoritative for DNS** and proxies traffic in front of Vercel, which hosts the app. Live DNS records (A/CNAME/MX/TXT) must be edited in the Cloudflare dashboard — not Vercel's or Hostinger's DNS editors. (Verify with `dig NS cardpop.com.au` before assuming — the nameservers have moved before: Hostinger → Vercel → Cloudflare.)

## Architecture

### Frontend (React SPA)

**Entry point**: `main.jsx` → `App.jsx`

All pages are lazy-loaded in `App.jsx` via React Router v7. The provider wrapping order in `App.jsx` matters: `AuthProvider` → `AdminProvider` → `CartProvider` → `CategoryHierarchyProvider`.

**Path alias**: `@/` resolves to the repository root (not `src/`). So `@/components/Header.jsx` maps to `./components/Header.jsx`.

**Pages** live in `pages/` with subdirectories for logical sections: `account/`, `admin/`, `blog/`, `collections/`, `community/`, `grading/`, `info/`, `marketplace/`, `markets/`, `shop/`, `vault/`.

**UI components** are shadcn/ui ("new-york" style, Radix UI primitives) in `components/ui/`. Add new shadcn components via the config in `components.json`. Icons are from `lucide-react`.

**Styling**: Tailwind CSS with CSS variable-based theming. The brand palette (see `tailwind.config.js`) is `brand-red` (#CE1126), `brand-charcoal`, `brand-silver`, `brand-lightgrey` and `brand-white` — **there is no blue in the branding guide**; don't introduce `brand-blue` or blue accents. Dark mode is class-based via `next-themes`.

**Toasts**: Use `sonner` via `import { toast } from 'sonner'`.

**Forms**: `react-hook-form` + `zod` for validation.

### Authentication & Authorization

`AuthContext` (`contexts/AuthContext.jsx`) is the single source of truth for auth state. It wraps Supabase Auth and exposes `currentUser`, `session`, `profile`, `isAuthenticated`, `loading`, and `profileLoading`.

- `ProtectedRoute` — redirects to `/login` if unauthenticated; accepts `requireVerification` prop.
- `ProtectedAdminRoute` — additionally requires `isAdmin` from `useAuth()` (which is `profile.is_admin`). **Never check `currentUser.role === 'admin'`** — the Supabase user's `role` is always `'authenticated'`, so that comparison is always false.

**Social login (OAuth)**: `components/OAuthButtons.jsx` surfaces Google / Apple / Facebook buttons via `supabase.auth.signInWithOAuth`; a provider only works once enabled in the Supabase dashboard. On first sign-in the `on_auth_user_created` trigger (`handle_new_user()`) creates the `profiles` row — hardened in `supabase/migrations/20260712010000_harden_handle_new_user_oauth.sql` so a Facebook login with no email can't fail the `username` NOT NULL/UNIQUE constraints. Provider setup, step by step, is in `docs/oauth-login.md`.

### Data Access (Frontend)

The frontend has two data sources:

1. **Supabase** (`lib/supabaseClient.js`) — direct Supabase JS client using the public anon key. Used for all user-facing data reads/writes via Row Level Security policies. Import as `import { supabase } from '@/lib/supabaseClient.js'`.

2. **Express backend** (`lib/apiServerClient.js`) — proxied via `/hcgi/api` (Vercel rewrites this to `/api`). Used for operations requiring server-side secrets: eBay pricing, Stripe payments, card OCR, AI chat, auth/MFA flows, newsletter subscription. Always sends the Supabase `access_token` as a Bearer header automatically.

### Supabase

Supabase hosts the PostgreSQL database and provides Auth. The project URL is `https://vrfsaazuqjxotnieqlkd.supabase.co`.

- **Migrations**: The repo is the source of truth. Every schema change is a new `supabase/migrations/<timestamp>_<name>.sql` file — **never edit production directly in the SQL editor** (that causes drift). The repo is linked to the project via `supabase/config.toml` (`project_id`). On merge to `main`, `.github/workflows/supabase-migrations.yml` runs `supabase db push --include-all`, which applies every migration whose version isn't yet in the project's `schema_migrations` table (`--include-all` lets an unrecorded straggler apply even if its version sorts below the newest remote one). **Always create new migrations with `supabase migration new <name>`** — it stamps a full `YYYYMMDDHHMMSS` UTC timestamp, which is collision-proof. Do NOT hand-number files (`..._000001`, `..._000002`, …): two branches open at once inevitably pick the same counter, and `db push` then dies on a duplicate `schema_migrations` primary key. **Never apply SQL through the dashboard / SQL editor / Supabase assistant** — a change made there is recorded under a version that has no repo file, which blocks *every* future `db push` (`Remote migration versions not found in local migrations directory`) until the history is reconciled by hand. Let the merge apply migrations; the repo is the only path to production schema. Locally: `supabase link --project-ref vrfsaazuqjxotnieqlkd` once, then `supabase db push` to apply. Rules: unique version prefixes (guaranteed if you use `migration new`); write idempotent DDL (`if not exists`, `create or replace`, `drop ... if exists`); keep changes backward-compatible so the schema can land before the app that uses it. CI needs two repo secrets: `SUPABASE_ACCESS_TOKEN` and `SUPABASE_DB_PASSWORD`. **A failed `db push` is not self-announcing** — Vercel deploys the frontend through its own Git integration, so the site keeps shipping against a stale schema and the only signal is a red run in the Actions tab. `.github/workflows/migration-drift.yml` is the safety net: daily (21:00 UTC) it runs `supabase migration list --linked` and fails if any repo migration is missing from `schema_migrations`, filing one tracking issue so the gap is visible without opening Actions. It re-fails every day until the drift is resolved. If it goes red, fix the underlying push failure and re-run **Supabase migrations**. (This exists because `db push` failed on every merge from 2026-07-22 to 2026-07-30 and 14 migrations sat unapplied for a week — including the one fixing `private.can_sell()`, which silently blocked every seller from listing.) (Note: `supabase db push` refuses to run while the project's `schema_migrations` table lists any *remote* version with no matching local file — the ~76 older dashboard-applied rows that pre-dated this repo were removed from tracking for exactly this reason, backed up to `supabase_migrations.schema_migrations_backup_20260703`. If that error returns after a manual dashboard change, reconcile with `supabase migration repair --status reverted <version…>` for the orphaned versions it names. Also: the whole `config.toml` must parse — an unknown key like `auth.enable_signups` fails every CLI command including `db push`.)
- **Frontend client** (`lib/supabaseClient.js`): Uses the public anon key. Security is enforced by RLS policies on the database.
- **Backend client** (`src/utils/supabaseClient.js`): Uses the service role key — bypasses RLS. Never expose this key client-side.
- **Manual backup & restore**: `scripts/backup-supabase.sh` produces a single timestamped archive (DB dump via `supabase db dump` + all Storage buckets except the sensitive `verification-docs`, via `scripts/backup-storage.mjs`) to drag into the "cardpop.com.au- site backup" Google Drive folder. Full procedure in `docs/backup-and-restore.md`. `backups/` is git-ignored — dumps hold real data/PII and must never be committed.
- **Changing region**: a project's region can't be changed in place — it's a new-project-in-`ap-southeast-2` + migrate + repoint operation with downtime. Full runbook (schema/data/auth/storage move and every hardcoded-ref repoint point) in `docs/database-region-migration.md`.

### External Integrations

- **Supabase** (`lib/supabaseClient.js`, `src/utils/supabaseClient.js`): Auth and database.
- **eBay** (`src/routes/ebay.js`, `src/utils/ebayClient.js`): Market price lookups with caching (`src/utils/ebayCache.js`).
- **Card identification** (`src/routes/card-ocr.js` → `src/routes/cardsight.js`): turning a listing photo into filled-in fields is a five-step pipeline, and **the order is load-bearing**. The photo is first rectified into a flat card image (`utils/analysisImage.js`, fail-safe — any problem keeps the original, and the seller's stored photo is never altered) so the vision models spend their downscale budget on the card rather than the background. OCR then runs *first* (Claude reads the card, grounded against the public TCG catalogue) because it is the only step that can name the category; that category then narrows CardSight to a **single segment**. Two rules exist to stop wrong cards being returned confidently: a collection CardSight has no catalog for (Magic, One Piece, AFL, NRL…) is **skipped entirely** rather than searched — every segment answers with its best guess *within that segment*, so searching a catalog that can't contain the card can only return the wrong one; and when the category is unknown the ten-segment fan-out is ranked by match specificity (exact card id > set-level) *before* confidence, since CardSight's confidence is a three-level enum that ties constantly and would otherwise let the fan-out array order pick the winner. Note that `confidence` is `"High" | "Medium" | "Low"`, **not** a number — always go through `utils/cardsightConfidence.js`. Full runbook: `docs/card-identification.md`.
- **Order pricing** (`src/services/commissionService.js`, `src/utils/processingFee.js`): a buyer pays item + commission + shipping + a **payment-processing fee**. **Every price is GST-inclusive** — no GST line is ever added to the buyer's bill; the checkout states "Includes GST of $X". `calculateGst()` splits that included GST by who supplied what: the seller's share (their card + their postage, 1/11 at 10%) is **deducted from their payout** and remitted by CardPop on their behalf, applied to **every seller and every transaction with no GST-registration test** (a deliberately conservative business decision — confirm the tax position with an accountant), while the GST inside CardPop's own commission and processing fee is money the platform already holds. The seller is paid `item − commission − their GST + shipping` and never sees the processing fee. `orders.gst_aud` means GST *added on top* and is now always 0; `gst_included_aud` / `seller_gst_aud` / `platform_gst_aud` carry the real figures, and `gst_on_commission_only` is retired. Checkout is **Australia-only**: `checkAustralianAddress()` (`src/utils/addressValidation.js`) gates both paths *before* the Amazon Location geocode, which fails open when `AWS_LOCATION_API_KEY` is unset, and the single-item session pins `shipping_address_collection` to AU; overseas *cards* are blocked in the webhook by `cardCountryPolicy.js` (`ALLOWED_CARD_COUNTRIES`, default `AU`) — Checkout captures on completion, so the block is a refusal to fulfil plus a full refund, and a Stripe Radar rule (`:card_country: != 'AU'`) is the cheaper front line because it declines before capture. Because CardPop is the merchant of record, Stripe's cut comes out of platform funds, so the processing fee is **grossed up** — `(rate × subtotal + fixed) / (1 − rate)`, rounded up — since Stripe charges its percentage on a total that includes the fee itself. Rates live in `platform_settings` (`processing_fee_enabled` / `_pct` / `_fixed_aud`, default 1.9% + $0.35) and are editable at Admin → Commission Settings. Checkout `payment_method_types` is **pinned** to `card,paypal` (`src/utils/checkoutPaymentMethods.js`) because Afterpay's ~6% would sell at a loss against a card-rate fee — override with `STRIPE_PAYMENT_METHOD_TYPES` if a pinned method isn't active on the account, since pinning an inactive one takes checkout down. Full runbook: `docs/order-pricing.md`.
- **Stripe** (`src/routes/stripe.js`): Payment processing and checkout. Seller payouts run on Connect via **separate charges and transfers** — the buyer is charged on the *platform* account, then `payoutService.js` pushes proceeds out with `transfers.create({ destination })` (or holds them in the seller's wallet until they onboard). New seller accounts are created with explicit **controller properties** (Managed Risk + Stripe-managed pricing + Express Dashboard) rather than `type: 'express'`, so Stripe — not CardPop — carries unrecoverable negative balances. Controller properties are **fixed at creation**, so sellers onboarded before this change stay platform-liable forever; `GET /connect/status` returns `lossLiability` per seller. The shape lives in one place (`src/utils/sellerAccountShape.js`) shared by the onboarding flow and the backfill script, and falls back to the legacy Express shape if Stripe rejects the configuration. Full runbook: `docs/stripe-connect.md`.
- **Stuck-payment reconciliation** (`src/services/pendingOrderAlertService.js`): an order row is written `pending` when its Checkout Session is created and only moves forward when `checkout.session.completed` reaches the webhook — so if that event never arrives, the buyer has paid and *nothing* happens, with no error anywhere. A GitHub Actions schedule (`.github/workflows/cron-reconcile-pending.yml`, every 2 hours at :15) hits `/api/stripe/reconcile-pending` (`CRON_SECRET` bearer, fail-closed) and asks Stripe directly whether each still-`pending` order's session is `paid`; any that are get raised to Sentry and to the admin notification bell (`order_payment_unfulfilled`, deduped on `related_id` so a repeat run can't spam). It **reports only** — replaying the missed event is a deliberate act in the Stripe dashboard, since fulfilment moves money. This exists because a live payment on 2026-07-16 sat unfulfilled for two weeks: five sibling events (`payment_intent.succeeded`, `charge.succeeded`…) processed fine seconds apart, but `checkout.session.completed` never landed. The cadence used to be capped by the hosting plan rather than the job: **Vercel's Hobby plan rejects any cron firing more than once a day** — a sub-daily schedule fails the whole deployment build (`Hobby accounts are limited to daily cron jobs`), which is how it silently blocked every production deploy once. That is why every schedule now lives in GitHub Actions instead and `vercel.json` has no `crons` block — see `docs/scheduled-jobs.md`.
- **Kit.com** (`src/routes/newsletter.js`): Newsletter subscriptions via the Kit v4 API. Requires `KIT_API_KEY` and `KIT_FORM_ID` env vars. The `/launch` pre-launch landing page subscribes with `list: 'launch'`, which targets `KIT_LAUNCH_FORM_ID` (optional — falls back to `KIT_FORM_ID` until set). Setting `VITE_COMING_SOON=true` at build time redirects the homepage to `/launch`. Kit publishes a **Developer Docs MCP server** (`https://developers.kit.com/mcp`) that gives Claude Code read-only, always-current access to Kit's API v4 reference, OAuth flow docs, App Store guidelines and plugin architecture — handy when working on this integration. It's an optional per-developer tooling convenience and is deliberately **not** committed to the repo, so it touches nothing at runtime: the production subscribe path stays the direct v4 REST call in `src/utils/newsletter.js`. To use it, add it at user scope once — `claude mcp add --transport http --scope user kit-docs https://developers.kit.com/mcp` — then authorize it via `/mcp` in an interactive Claude Code session (it cannot be authorized in a headless/web session). (Kit also publishes a separate *operational* MCP at `https://app.kit.com/mcp` that manages the live account — forms, subscribers, broadcasts — and requires a paid Kit plan; deliberately unused here to avoid an agent mutating real subscriber data.)
- **Resend** (`src/utils/emailService.js`): **Transactional** email — the automated, server-triggered messages sent to one recipient in response to an event: order confirmed (buyer), item sold (seller), refund processed/issued, the registration welcome offer, the **offer/enquiry received** alert a seller gets when a buyer makes an offer on their listing, and the **order shipped** email with the carrier tracking link (Admin → Order Management → Mark as Shipped → `POST /admin/orders/:id/ship`; carriers/links in `utils/shipmentTracking.js`) (fired from `stripeWebhookService.js`, `refundService.js`, `welcomeOfferService.js`, `routes/offers.js`, `routes/admin.js`). Requires `RESEND_API_KEY`; sends from `noreply@cardpop.com.au`. This is a distinct role from the other two mail systems and does not overlap: **Google Workspace** is the human inbox (person-to-person mail) and **Kit.com** is bulk marketing (newsletters/campaigns). Sending requires the domain to be **verified in Resend** — its SPF/DKIM DNS records live in Cloudflare and coexist with Google's (Resend uses the `send.` subdomain + `resend._domainkey`, Google uses the root domain + `google._domainkey`). Supabase Auth emails (signup confirmation, password reset, magic links) are a separate pipeline sent by Supabase itself, not Resend. Full setup and DNS records: `docs/email.md`. If `RESEND_API_KEY` is unset the service logs a warning and silently skips sending (fail-safe).
- **Anthropic Claude API** (`src/utils/blogArticleGenerator.js`): nightly blog article generation. A GitHub Actions schedule (`.github/workflows/cron-blog-generate.yml`) hits `/cron/blog-generate` (→ `api/blog-generate.js`, its own 300s function — the 40s `api/index.js` budget is too short) with the `CRON_SECRET` bearer. It claims the highest-priority row from the `blog_article_topics` queue, builds a factual base from that topic's `tracked_cards` price snapshots (`blogPriceContext.js`), and asks Claude for a draft under a structured-output schema. Every draft is checked by `blogStyleGuard.js` — banned AI-tell vocabulary, sentence-length variance, word floor, and **every dollar figure must trace back to a real snapshot** — with one retry that feeds the violations back. Drafts land in `blog_articles` unpublished unless `BLOG_AUTOPUBLISH=true`. Topics whose price history is too shallow are put back in the queue and the run moves to the next candidate. Full runbook: `docs/blog-automation.md`.
- **Automated event scanning** (`src/utils/eventScanner.js`): nightly discovery of Australian trading-card events. A GitHub Actions schedule (`.github/workflows/cron-event-scan.yml`) hits `/cron/event-scan` (→ `api/event-scan.js`, its own 300s function) at 17:07 UTC Sunday = **3am AEST Monday**. One Claude call with the `web_search_20260209` server tool runs the queries in `event_scan_sources`; candidate URLs are harvested from the search-result blocks (not the model's prose), recorded in `event_scan_candidates` (unique on `url` — a page is fetched and extracted **once ever**, which is the job's main cost control), then each new page is pulled through the shared SSRF-safe fetcher (`src/utils/safeFetch.js`) and extracted under a JSON schema using the same `EventScraperPrompt` as the admin scraper. Results land in `events` as `pending_review` with `auto_discovered = true` — **nothing is ever published automatically**. Gates reject undated, past, over-400-days-out, non-event and duplicate pages. `api/event-scan.js` accepts *either* the `CRON_SECRET` bearer *or* a signed-in admin's Supabase token, so the admin panel's "Run scan now" button can call the 300s function directly without the secret reaching the browser. Admin UI is `components/EventScanPanel.jsx` in Admin → Event Management. **Per-event weekly re-scan**: an event's "Website to scrape" (`events.source_url`, `components/EventSourceWatchPanel.jsx` in the event form) is scanned on save and then every 7 days by a daily job (`.github/workflows/cron-event-watch.yml` → `/cron/event-scan?mode=watches`, engine `src/utils/eventSourceWatcher.js`, state in `event_source_watches`) — it fills in only fields the event has **blank**, and queues changed dates/venue/price as pending changes for an admin to apply or dismiss; it never overwrites. Full runbook: `docs/event-scanning.md`.

### Image serving & Supabase egress

Supabase meters ALL storage egress (including its own CDN's cache hits) against the plan quota, so image traffic is managed in three layers (see `docs/image-cdn.md`):

1. **Immutable uploads with long cache headers**: every storage upload uses a timestamped filename and `cacheControl: '31536000'`. Never reuse a storage path for changed content — upload to a new timestamped path and update the DB reference (avatars etc. already work this way). `scripts/backfill-image-cache-headers.mjs` retrofits old objects.
2. **Service worker** (`public/sw.js`): storage image URLs (`/storage/v1/object|render/image/public/`) are cached cache-first on the client (capped, oldest-first eviction), so returning visitors generate ~no image egress.
3. **CDN in front of Supabase Storage** — a Cloudflare Worker on `img.cardpop.com.au` (source: `cloudflare/image-proxy-worker.js`, deployed via the Cloudflare dashboard): when `VITE_IMAGE_CDN_HOST` is set, `utils/imageUrl.js` rewrites storage URLs onto the CDN. The same Worker also exposes a `/card-art` passthrough that caches third-party card art (Pokémon TCG / Scryfall / YGOPRODeck) into R2 so it's insulated from those upstream CDNs — activated by `CARD_ART_CDN_HOST`, see `docs/image-cdn.md`. **At render time, always build image URLs via `publicImageUrl(pathOrUrl, bucket?)` or `getCardImage()` from `utils/imageUrl.js` — don't call `supabase.storage.getPublicUrl()` directly.** Exception: URLs *stored in the DB* (e.g. `image_url` columns written by admin forms) intentionally stay canonical Supabase URLs so the CDN host can change later.
4. **Pre-generated grid thumbnails**: card image uploads also store a 480px WebP companion thumb at `<path minus ext>.thumb.webp` (`createThumbnail` / `thumbStoragePath`); `getCardImage` emits `thumbSrc` for uploads after `THUMBNAILS_SINCE` (timestamped filenames make this derivable without a DB column) and `CardImage` tries it before the full image. See `docs/image-cdn.md`.

### Security boundaries (read before touching auth, money or offers)

Full findings live in the dated `SECURITY_AUDIT_*.md` files (latest: `SECURITY_AUDIT_2026-09-21.md`). The rules those audits established:

- **MFA is enforced server-side, not just in the UI.** `requireAal2` (`src/middleware/requireAal2.js`) rejects an AAL1 token from any user who has a verified MFA factor; `requireAdmin` = auth + `isAdminUser` + `requireAal2`. It is mounted on the whole `/admin` router and every other admin surface (`blog`, `event-scan`, `reports`, `event-scraper`, the manual scan trigger in `api/event-scan.js`), **and** on the user-facing money/recovery routes: `/stripe/connect/{onboard,dashboard-link,withdraw}`, `/wallet/{topup,save-card}`, `/auth/password/change`, `/auth/backup-codes/generate`. Never add an admin or money-moving route with a bare `isAdminUser()`/`authMiddleware` check.
- **The refund policy has one source: `utils/buyerProtectionPolicy.js`.** Marketplace: a sale is binding when the card is as advertised (no change of mind); not-as-described / damaged / counterfeit / never-arrived claims within **7 days of delivery** (or after 7 days unposted, hard cap 45 days from purchase) are refunded **in full, fees included**, and the seller's payout is reversed. Shop: 14 days from delivery, change of mind fine (`utils/shopReturnPolicy.js`, mirrored in Google Merchant Center). `refundWindow()` drives the Request Refund button *and* `POST /refunds/request`; `computeRefundAmounts()` defaults to retaining nothing (admin knobs `refund_fee_retention_pct` / `refund_retain_processing_fee`). The Returns, Trust & Safety, Safe Buying, Shipping and FAQ pages, `BuyerProtection`, `CheckoutReassurance`, `RefundPolicyNote`, Account → Orders and the prerendered copies in `api/prerender.js` all read `PROTECTION_COPY` / the policy constants — never type a day count or a refund promise into a page.
- **Marketplace buying is gated by value, not blanket ID.** Any order with a marketplace listing needs a signed-in, email-confirmed buyer; Stripe Identity is required only once the marketplace items reach `marketplace_identity_threshold_aud` (platform setting, default $500, `0` = every order). The rule is one dependency-free function, `utils/marketplaceIdentity.js`, used by the checkout page, the cart drawer and the product page to *say so before the till*, and enforced server-side by `src/middleware/requireIdentityForPurchase.js` (which prices the listings from the DB, never from the request). Shop items are never gated; a mixed cart can pay for its shop lines while the cards wait. Return paths: the gate sends sign-ups to `/signup?next=/checkout`, which rides inside the confirmation link (`/welcome?next=…`, validated by `lib/safeInternalPath.js`).
- **Payment return URLs are allow-listed.** Every `success_url` / `cancel_url` / `return_url` / `refresh_url` handed to Stripe, Connect or PayPal goes through `invalidReturnUrl()` in `src/utils/returnUrl.js` — the origin must be `APP_URL`, a `CORS_ORIGIN` entry, Vercel's own deployment URL, or `CHECKOUT_RETURN_ORIGINS`. An attacker-chosen `success_url` is a phishing hop on the back of a genuine payment.
- **New offers can't be born accepted.** The offers INSERT policy only checks buyer/listing/seller, so until `20260928071648_binding_offers_lifecycle.sql` a buyer could insert `status = 'accepted'` straight from the browser and `resolveOfferPrice()` would check out at that self-chosen price. The insert trigger now forces `pending`, clears any counter and stamps the 48h expiry — never let a client choose lifecycle columns.
- **Offers derive their seller from the listing.** `POST /offers` ignores a body `sellerId` that doesn't match `listings.seller_id`, `resolveOfferPrice()` refuses an offer whose `seller_id` isn't the listing's seller, and the DB enforces the same with a BEFORE INSERT trigger + restrictive policy (`20260921210000_offers_bind_seller_to_listing.sql`). Before this, a buyer could name an accomplice as "seller", have them accept, and buy any card for $1.
- **Outbound fetches of untrusted URLs go through `src/utils/safeFetch.js`** — never plain `fetch()`. Its guard parses hosts with `ipaddr.js` (bracketed IPv6 and hex IPv4-mapped literals used to bypass it), re-checks every redirect hop, and caps the body at 2 MB under the timeout.
- **Sentry never receives request bodies/headers.** `scrubSentryEvent` in `src/app.js` drops `request.data`, cookies and auth headers and filters secret-shaped keys — a 5xx in `/auth/password/change` used to ship both passwords and the bearer token.
- **There is no server-side password-reset endpoint.** Resets go straight from the browser to Supabase with a Turnstile token; a service-role copy bypassed CAPTCHA (email bombing) and was removed.
- **Never re-add `.github/workflows/db-region-migrate.yml`** (or any workflow that runs `drop schema public cascade` against the live project ref). It was removed because a push to a branch name was enough to wipe production. The `SUPABASE_*_TOKYO` / `SUPABASE_*_SYDNEY` repo secrets it used should be deleted and the Sydney DB password + service-role key rotated.

### Analytics, consent & ads

GA4 (`lib/analytics.js`) sends page views **and the ecommerce funnel** — `view_item`, `add_to_cart` (inside `useCart.addToCart`, so every button is covered), `begin_checkout`, `add_payment_info`, `purchase` (deduped per Stripe session id). New buy buttons must go through `useCart` rather than writing cart state directly, or the funnel loses the step. **Product structured data must carry a global identifier** (Search Console's Merchant listings report warns on any `Product` with no `gtin`/`mpn`/`brand`): every Product node, in `api/prerender.js` and the SPA pages alike, builds `brand` / `sku` / `mpn` / `gtin` through `utils/productIdentifiers.js` — shop rows from `shop_products.brand` (blank = CardPop) + `sku` + `barcode` (only a well-formed GTIN is emitted), single cards from the franchise + set/card number — never hand-write a `brand` or `gtin` into a page, and never put a non-GTIN string under `gtin`. `tests/backend/productMarkupIdentifiers.test.js` fails CI for any Product node that doesn't spread one of those helpers, and `npm run check:merchant-listings` (weekly in `.github/workflows/merchant-listings-check.yml`, files an issue on failure) checks the live pages' markup the way Googlebot sees it. Google Ads and the Meta Pixel are **consent-gated**: `components/CookieConsentBanner.jsx` writes `lib/consent.js`, and both tags stay dormant until *Accept all* (GA4 runs regardless, with Consent Mode v2 ad-storage denied until then). **AdSense never loads on a buying surface** — `NO_AD_PREFIXES` in `lib/adsense.js` excludes the homepage, shop, marketplace, product, prices, collections and seller pages so an Auto-ads unit can't put a competitor's listing beside Add to Cart; ads earn on blog/events/guides only. Full notes: `docs/seo-analytics.md`.

### DDoS & abuse protection

Cloudflare (proxying all traffic) is the volumetric DDoS layer; Express rate limiters (`src/middleware/global-rate-limit.js`, `src/middleware/endpoint-rate-limit.js`) handle targeted abuse. `src/app.js` sets a `trust proxy` function that trusts Cloudflare's published edge ranges (`src/utils/cloudflareIps.js`) so `req.ip` is the real visitor, not a Cloudflare edge IP — every IP-keyed control depends on this. Dashboard-side settings (Bot Fight Mode, WAF, edge rate-limit rule, Under-Attack playbook, Supabase quota hardening) are documented in `docs/ddos-protection.md`.

### Realtime discipline

Supabase Realtime keeps a WAL poller running for as long as *any* client holds a `postgres_changes` subscription, and it was the single largest consumer of DB time on the project because public pages subscribed anonymous visitors. Rules: **no realtime channel for anonymous visitors** — public grids and the live ticker refetch on return to the tab via `hooks/useRefreshOnReturn.js` instead; **shared state has one provider** (`contexts/NotificationsContext.jsx` for notifications, `WatchlistContext` for watchlist ids) — never open the same topic from two components, because `supabase.channel(topic)` returns the existing channel and the second `.on()` throws; **per-mount topics are unique** — wrap the topic in `uniqueTopic()` from `lib/realtimeTopic.js` for any subscription an effect may re-create, since a channel stays registered until its leave completes and a repeated topic binds to the dying one; **filter every binding to the viewer's rows and debounce bursts** into one refetch. Full notes: `docs/performance.md` → "Realtime discipline".

### Homepage performance

Every document paints from a static shell: "/" from `tools/home-shell.html` (header + hero), every other route from `app.html`, whose shell `tools/appShell.mjs` derives from the homepage shell at build time (same header, announcement bar and cookie banner, with the `PageLoader` markup in place of the hero — keep `PageLoader.jsx` and `APP_SHELL_MAIN` in sync; a test checks). Both get critical CSS inlined by beasties (`inlineCriticalCss` in `vite.config.js`), `app.html` also carries a per-route chunk preload map (`ROUTE_PRELOADS` → `data-route-preload`, matched against `location.pathname` by the bootstrap), and the CSP bootstrap starts the JS/CSS fetches **one frame after the first paint** — Lighthouse's simulation otherwise counts every preload as render-blocking. Every non-essential third party (Sentry, gtag, Cloudflare beacon, Impact, the Google reviews badge) loads via `lib/deferredLoad.js` on the first interaction or 8 s after `load`, never at idle, so it stays out of the window PageSpeed measures. Homepage Supabase reads start in `main.jsx` (`lib/homepageData.js`) before React mounts. Changing `CSP_BOOTSTRAP` means updating its sha256 in **both** CSP headers in `vercel.json` (the build and `tests/frontend/homeShell.test.js` both check). Full notes: `docs/performance.md`.

### Deployment

Vercel's **native Git integration** builds and deploys on every push to `main`
(and creates preview deployments for pull requests) — no GitHub Actions step is
involved in deploying:

```
git push main
  → Vercel builds dist/ and serves api/index.js as a serverless function
```

GitHub Actions does not deploy. It runs the quality gates —
`.github/workflows/ci.yml` (lint + tests + build) and `e2e.yml` on pull
requests, `.github/workflows/main-ci.yml` re-running the same `verify` gate on
pushes to `main` — and it drives the **scheduled backend jobs** (price
refresh, payment reconciliation, blog generation, event scan, supplier price
watch, GA4 site-traffic sync) that used to be
Vercel Cron entries. Those moved off Vercel because the Hobby plan rejects any
cron firing more than once a day; `vercel.json` now has no `crons` block and the
schedules live in `.github/workflows/cron-*.yml`. They need a `CRON_SECRET`
Actions secret matching Vercel's, and — since this repo is private — they spend
metered Actions minutes, billed a whole minute per run. Full runbook:
`docs/scheduled-jobs.md`. The old `deploy.yml` (which ran `vercel --prod` via the CLI using an AWS
OIDC role + SSM-stored token) was removed when deploys moved to Vercel's Git
integration; the AWS role and `/cardpop/vercel/*` SSM parameters are now unused
and can be cleaned up.
